# Безопасность MapLink

Документ описывает реальное положение дел: что закрыто, что закрыто быть не может без
бэкенда, и как жить с последним.

## Модель угроз

Проект — подарок конкретному человеку, данные не секретные. Но приложение публичное:
URL лежит на GitHub Pages, anon key виден в `index.html`, а значит им может воспользоваться
кто угодно. Отсюда три класса проблем, которые имели смысл:

1. **Stored XSS** — любой пользователь базы мог подставить HTML в `username`, `note`,
   `city`, `country`, `avatar_url` и выполнить JS у всех, кто это увидит (лента друзей,
   рейтинг, профиль). С anon key это означало: чтение и запись **от имени чужих строк**.
2. **Мусор и спам в базе** — прямой заход на URL создавал строку «гостя» в `users`,
   любой желающий мог заспамить `places`/`comments`, строки не были скоупены по владельцу.
3. **Слабые места логики** — инвайт-код на `Math.random`, запросы к Nominatim без
   троттлинга, `alert()` с текстом ошибки БД.

## Что сделано

### Экранирование на всех путях вывода

Все данные из внешних источников проходят через хелперы в начале `__maplinkMain()`:

| Хелпер | Зачем |
|---|---|
| `esc(v)` | HTML-escape для текста внутри разметки (`& < > " ' \``) |
| `escAttr(v)` | То же для значений атрибутов (кавычки уже в таблице) |
| `safeId(v)` | Оставляет `[A-Za-z0-9_-]`, ≤64 симв. — для uuid в атрибутах и inline-обработчиках |
| `safeImgUrl(u)` | Пропускает только `http(s):`, `data:image/`, `blob:`; всё остальное → `''` |
| `clip(v, n)` | Срезает управляющие/невидимые символы (в т.ч. zero-width, bidi), схлопывает пробелы, режет длину |
| `escMultiline(v, n)` | `esc(clip())` + перевод `\n` в `<br>` — для заметок |
| `safeDate(v)` | Дата как `[\d.\-/]`, не длиннее 10 символов |
| `cleanName/City/Country/Note/Date` | То же самое **на запись**, с лимитами из `LIMITS` |

Правило для нового кода: либо `el.textContent = value`, либо шаблон с `esc(...)`.
Третьего нет. Проверка не даёт об этом забыть — `tools/verify` падает, если payload
превращается в живой элемент.

Отдельно: строки рейтинга больше не несут `onclick="window.__openFriend('<имя>','<аватар>')"` —
данные читаются из `data-*`, потому что escape в JS-строке внутри HTML-атрибута это
слишком хрупкая конструкция для «просто экранируй».

### Запись только из Telegram

`__installReadOnlyGuard()` подменяет `window.fetch`: любой не-GET к `*.supabase.co`
вне Telegram получает локальную «405» с телом в формате PostgREST. Сделано на уровне
транспорта, а не на уровне 15 мест вызова, — новый код не сможет это обойти по забывчивости.
`Response` не используется (в старых WebView его может не быть) — возвращается plain-объект
с `ok/status/text()/json()`.

Плюс `initUser()` в этом режиме вообще не создаёт строку в `users`.

### Скоуп по владельцу

`update`/`delete` мест теперь идут с `.eq('user_id', myUserId)`. Это не защита от
взломщика с anon key (для него любые скоупы — формальность), но приложение больше
никогда не изменит чужую запись по случайному/подставному id.

### Прочее

- Инвайт-код: 10 символов из крипто-алфавита без похожих букв (`crypto.getRandomValues`
  с фолбэком на `Math.random`), а не 9 из `Math.random().toString(36)`.
- `startapp`-параметр принимается только по маске `[A-Za-z0-9_-]{4,16}`.
- CSP в `<meta http-equiv>`: `connect-src` разрешает только наши источники, поэтому даже
  если в DOM когда-нибудь окажется чужой скрипт, выгружать данные ему будет некуда.
  `style-src`/`script-src` содержат `unsafe-inline` — платой за single-file архитектуру.
- Nominatim: очередь с интервалом ≥1.1 с и отменой устаревших запросов (`AbortController`) —
  это и вежливость к публичному сервису, и защита от собственного rate-limit.

## Чего этот проект закрыть на клиенте не может

`users.username` и всё остальное пишутся с anon key. RLS-политика не может проверить
«эта строка принадлежит этому telegram_id», потому что в JWT анонима нет никакого
субъекта. Никакой клиентский код не доказывает личность: `initDataUnsafe.user`
— это то, что прислал сам клиент.

Единственные честные варианты (по возрастанию цены):

1. **Per-install секрет + политики** (`supabase/migrations/0001_optional_device_secret.sql`):
   приложение при первом запуске генерит секрет, кладёт его хэш в свою строку `users`,
   и дальше каждый запрос идёт с заголовком `x-ml-secret`; политики Require по нему.
   Плюс: не нужен бэкенд. Минусы: секреты лежат в localStorage WebView (слишком живучи
   для XSS, но XSS у нас закрыт), и нужна проверка CORS на кастомный заголовок.
2. **Edge Function, проверяющая initData** (`supabase/functions/verify-telegram/`):
   бот-токен известен только серверу, поэтому подпись `initData` проверяется там,
   и функция выдаёт короткий JWT, под которым уже работают честные RLS-политики
   `auth.uid() = user_id`. Это правильный путь, если в приложение придут чужие люди.
3. Ничего не менять, если приложение остаётся «на двоих» — спам в свою же базу
   владельцу не страшен, а XSS и read-only гейт закрывают основные реальные риски.

Пока выбран вариант 3 + закрытые 1–2 пункта из «что сделано». **Не ужесточай RLS
вслепую**: сломается всё приложение, и это не поймает ни одна проверка из `tools/verify`.
